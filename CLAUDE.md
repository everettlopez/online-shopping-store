# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Online store: a FastAPI + SQLModel backend (`app/`) on MySQL with Alembic migrations and Stripe Checkout, plus a React + TypeScript + Vite frontend (`frontend/`). Development is on Windows; the Python virtualenv is `venv/` in the project root.

## Commands

All from the project root.

```bash
venv\Scripts\pip install -r requirements-dev.txt        # backend + test dependencies
venv\Scripts\alembic upgrade head                       # apply migrations (reads DATABASE_URL from .env)
venv\Scripts\alembic revision --autogenerate -m "..."   # after changing a model; review the file before upgrading
venv\Scripts\python -m uvicorn app.main:app --reload    # API on :8000 (docs at /docs)
npm --prefix frontend run dev                           # frontend on :5173
stripe listen --forward-to localhost:8000/api/payments/webhook --events checkout.session.completed,checkout.session.async_payment_succeeded,checkout.session.async_payment_failed,charge.refunded
```

Run the API in its own terminal on Windows: when uvicorn auto-reloads, it sends Ctrl+C to every process in that terminal.

Tests (backend only; no MySQL, `.env` or network needed):

```bash
venv\Scripts\python -m pytest                                              # whole suite
venv\Scripts\python -m pytest tests/api/test_cart_api.py                   # one file
venv\Scripts\python -m pytest tests/api/test_cart_api.py::test_clear_cart  # one test
venv\Scripts\python -m pytest -k checkout -x                               # by name, stop at first failure
```

Frontend: `npm --prefix frontend run lint` (ESLint; it must report no problems, and CI runs it) and `npm --prefix frontend run build` (runs `tsc -b`, so it is also the type check). The frontend has no test runner.

`.claude/launch.json` defines the `api` and `dev` preview servers.

`venv\Scripts\python -m app.create_admin <email>` makes a registered account an admin (`app/create_admin.py`); it's how a new store gets its first admin.

## Configuration

Settings come from the environment or `.env` (see `.env.example`). Required: `DATABASE_URL`, `JWT_SECRET_KEY` (at least 32 chars), `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`. Optional deployment settings are in `app/settings.py`: `STORE_NAME` (used in emails), `FRONTEND_URL`, `PUBLIC_API_URL`, `CORS_ORIGINS`, `COOKIE_SAMESITE`, `COOKIE_SECURE`, `ENABLE_DOCS`, `SQL_ECHO` and `UPLOAD_DIR`, plus the shipping and tax settings `SHIPPING_FLAT_RATE`, `FREE_SHIPPING_THRESHOLD`, `STRIPE_AUTOMATIC_TAX` and `STRIPE_PRODUCT_TAX_CODE`, and the email settings `RESEND_API_KEY`, `EMAIL_FROM`, `ORDERS_EMAIL_FROM`, `ACCOUNT_EMAIL_FROM`, `EMAIL_REPLY_TO` and `PASSWORD_RESET_MINUTES`, the alert and logging settings `ALERT_EMAIL` and `LOG_LEVEL`, and the rate limits `AUTH_RATE_LIMIT_PER_MINUTE`, `LOOKUP_RATE_LIMIT_PER_MINUTE` and `CHECKOUT_RATE_LIMIT_PER_MINUTE`. Their defaults suit local development. The frontend reads the API address from `VITE_API_URL` at build time (`frontend/.env.example`), falling back to the local API, and the store's identity from the other `VITE_*` variables there.

The project is meant to be an open-source store that anyone hosts by setting env values, so never hard-code a store's name, domain or email addresses: add a setting instead (`app/settings.py` for the API, a `VITE_*` variable read in `frontend/src/config/store.ts` for the storefront) and document it in the matching `.env.example`.

Deployment: the root `Dockerfile` builds the API (`docker/start-api.sh` migrates, then runs uvicorn), and `frontend/Dockerfile` builds the storefront served by nginx with an SPA fallback. `deploy/` is the single-server kit: `docker-compose.yml` (API with no published port, storefront, Caddy, and an optional `mysql` profile), the `Caddyfile` (HTTPS, security headers, a CSP that starts report-only, a request body cap) and `.env.example` for the domains and storefront build args; the API's settings go in `deploy/.env.api`, and a managed database's CA certificate in `deploy/certs/` (mounted at `/srv/certs`). Both env files and `deploy/certs/` are gitignored. Caddy sends the API a single `X-Forwarded-For` (`{client_ip}`), because uvicorn with `FORWARDED_ALLOW_IPS=*` takes the leftmost entry; `TRUSTED_PROXIES` (Cloudflare's ranges) is the only way to trust another proxy's address. The owner-facing walkthrough is `docs/hosting.md` and the launch checklist `docs/launch-checklist.md`; `deploy/check.sh` (POSIX sh, reads `deploy/.env`) checks a running store from outside. Keep all three in step with the kit and the API (for example, a new production setting may deserve a check). CI is `.github/workflows/ci.yml`, which also validates the compose file and Caddyfile. The README's Deployment section lists the production settings.

The functions in `app/settings.py` read the environment each time they're called, which is how tests change settings with `monkeypatch.setenv`. Some values are still read once when a module is imported: `DATABASE_URL`/`engine` (`app/db/session.py`), `SECRET_KEY` (`app/auth/core.py`, which refuses to sign or verify tokens with a key under 32 characters), and the Stripe key and `WEBHOOK_SECRET` (`app/routes/payments.py`).

## Backend architecture

- **App setup:** `app/main.py` has `create_app()`, which mounts every router under `/api`, adds `GET /api/health` (503 when the database is unreachable) and serves the upload folder (`UPLOAD_DIR`, default `app/uploads`) at `/uploads`. It also adds the CORS middleware and a CSRF guard that rejects POST/PUT/PATCH/DELETE requests from an `Origin` outside `CORS_ORIGINS` (requests with no `Origin`, such as Stripe's webhook, pass). On startup it runs `check_required_settings()`, then `seed_database()`. The latter refuses to start unless the database is at the Alembic head revision, then seeds the default categories into an empty table.
- **Layers:**
  - `app/models/` holds the SQLModel tables.
  - `app/schemas/` holds the Pydantic request and response models.
  - `app/database/` holds shared query helpers, named `database_*`.
  - `app/routes/` holds the routers.
  - The schema is owned by Alembic (`alembic/versions/`, whose `env.py` imports every model). Never add `create_all` to the app.
- **Response shapes:** `ProductRead` nests the full `category`, so build products with `database_get_product_reads()` (`app/database/products.py`) instead of returning `Product` rows. Orders are built with `build_order_reads()` in `app/routes/order.py`.
- **Auth:**
  - Login sets an httponly `shop_token` JWT cookie (PyJWT, HS256, 60 minutes) through `set_auth_cookie`/`clear_auth_cookie` in `app/auth/core.py`. Use these helpers so the cookie attributes match. A `Bearer` header also works.
  - Passwords are hashed with bcrypt itself (`hash_password`/`verify_password` in `app/auth/core.py`; no passlib), using a password's first 72 bytes as bcrypt always has, so hashes made before still verify.
  - Make login tokens with `create_user_token(user)`, which adds the user's `token_version` as the `ver` claim; `user_from_token()` rejects a token whose `ver` doesn't match (a missing `ver` counts as 0) with a 401. `revoke_sessions(user)` raises the version, ending every session the user has; the caller commits. It runs when the user changes their password (`PUT /auth/me/password`, which then sets a fresh cookie so that browser stays logged in), when a reset link is used, when an admin sets the user's password, and on `POST /auth/logout-all`.
  - Use `CurrentUser` for a logged-in user, `OptionalUser` where guests are welcome too (it gives `None` for no token or an invalid/expired one, so a stale cookie never blocks a guest), and `Depends(admin_required)` (`app/auth/dependencies.py`) for admin routes.
  - Resources owned by a user return 404, not 403, to anyone other than the owner (or an admin).
- **Orders exist only through Stripe Checkout:**
  1. `POST /payments/create-checkout-session` (`OptionalUser`) checks and prices what's being bought with `price_items()` (positive quantities, active products, stock), totalling quantities per product. A logged-in shopper checks out their server cart with two saved address ids. A guest sends `items` (their browser cart, product ids and quantities only), and Stripe Checkout collects their email, US shipping and billing addresses, and phone.
  2. It stores a `[product_id, qty, unit_cents]` snapshot, one entry per product, in the session metadata (Stripe allows 500 characters per value), with `user_id` and the address ids for an account or `guest: "1"` for a guest. It sends Stripe one line item per product (prices exclude tax), a flat shipping rate from `shipping_cents()` (free from `FREE_SHIPPING_THRESHOLD`), and, with `STRIPE_AUTOMATIC_TAX` on, `automatic_tax`, plus for accounts the user's Stripe Customer from `get_stripe_customer()`, whose shipping address Stripe Tax uses (for guests Stripe Tax uses the address they enter). Only US shipping addresses are accepted.
  3. `fulfill_checkout()` creates the order from that snapshot, not from the current cart, and records Stripe's subtotal, shipping, tax and total on it. A guest order has no `user_id` or address ids; its email, name and addresses come from the session's `customer_details` and shipping details (`collected_information.shipping_details` on newer Stripe API versions, top-level `shipping_details` on older ones such as the CLI's). Both the webhook and `GET /payments/session/{id}` call it as a fallback, so it is idempotent per `stripe_session_id`: accounts lock their cart row, and the unique `stripe_session_id` catches a racing guest fulfillment (`already_fulfilled()` rolls ours back).
  4. `GET /payments/session/{id}` shows an account's order only to its owner (or an admin), and a guest order to whoever has the session id, which only the buyer's browser gets back from Stripe. It also returns the order's `access_token` for the success page's tracking link.
  5. Slow-settling payments (bank debits): the order is created `pending` without a confirmation. `checkout.session.async_payment_succeeded` makes it `placed` and sends the confirmation; `checkout.session.async_payment_failed` makes it `cancelled` and restocks it. Both go through `settle_payment()`, which calls `fulfill_checkout()` first because Stripe may deliver them before `checkout.session.completed`.

  There is deliberately no route that creates an order or charges an amount supplied by the client; tests in `tests/api/test_security.py` check that.
- **Money:** prices and amounts are `DECIMAL(10,2)` columns (`Decimal` in the models) and cents when talking to Stripe; convert with `to_cents`/`from_cents` in `app/money.py` and never do money arithmetic in `float`. API schemas expose them as `float` so JSON keeps numbers. Order items keep the `unit_price` paid, which the order pages show instead of the product's current price.
- **Order tracking without an account:** every order gets a random `access_token`. The emails link to `/track/{order_number}?token=...` in the frontend, which calls `GET /orders/track/{order_number}?token=`. `POST /orders/lookup` turns an order number plus the order's email (case-insensitive) into that link, with the same 404 when either is wrong. `OrderRead` never includes the token. Guest orders never join an account, even one with the same email, because guest emails aren't verified.
- **Addresses on orders:** `fulfill_checkout()` copies both addresses onto the order (`Order.shipping_address`/`billing_address` JSON, shaped like `OrderAddress` in `app/schemas/address.py`, built with `address_snapshot()`, or `stripe_address_snapshot()` for a guest's Stripe-collected address; guest orders have no saved address ids). Responses show that copy, so editing a saved address never changes a past order. Deleting an address only sets `deleted_at` (listing, editing and checkout ignore it), because orders and checkouts in progress still reference the row.
- **Refunds:** `POST /orders/{id}/refund` (admin) refunds some or all of an order through `stripe.Refund.create` while holding the order's row lock, and `charge.refunded` (`sync_refund()` in `app/routes/payments.py`) records refunds made in Stripe's Dashboard. Both go through `record_refund()` in `app/routes/order.py`: `Order.refunded_amount` is set to Stripe's running total (so redelivered events change nothing), and the first time it reaches the order's total the order becomes `refunded`, gets `refunded_at` and is restocked (the button's `restock` can opt out; Dashboard refunds always restock). Partial refunds never restock. `restock_order_items()` returns an order's items once, recorded in `restocked_at`. The status `refunded` can't be set by hand, and only orders that were never paid (`was_paid()`) can be deleted (409 otherwise). Each refund emails `build_refund_email()`.
- **User deletion:** deleting a user goes through `database_user_has_orders`/`database_delete_user` (`app/database/users.py`). Users with orders are kept, since orders are financial records. Likewise, a product that appears in an order can't be deleted (409); admins set it inactive instead.
- **Email:** `app/mail.py` builds messages (`build_*_email`) while the request still has the database, and routes queue `send_email` as a FastAPI `BackgroundTask`. `send_email` logs failures and never raises. It goes through Resend, or prints the message when `RESEND_API_KEY` is empty. Each builder sets the message's sender: order and shipping emails use `orders_email_from()` and account emails `account_email_from()`, both falling back to `EMAIL_FROM`; every email gets `EMAIL_REPLY_TO` as its reply-to when set. Order emails go to `Order.email` (the account's email at checkout, or the one a guest gave Stripe) and link to the order's tracking page via `order_link()`. Order confirmations go out only when `fulfill_checkout()` creates a paid order or `settle_payment()` settles a pending one, so the webhook and success page don't send duplicates. Shipping notices go out from `PUT /orders/{id}/tracking`.
- **Logging and alerts:** `create_app()` calls `configure_logging()` (`app/logging_config.py`), which gives the app and uvicorn one format, `time level logger message`, at `LOG_LEVEL`. Each module logs with `logger = logging.getLogger(__name__)`, one line per event with details as `key=value` (`order created order_id=5 status=placed`). Log ids, never customers' emails, addresses or tokens. `print` is only for the command-line tools and the console stand-in for email. `alert_admin(key, subject, details, background_tasks=None)` (`app/alerts.py`) emails `ALERT_EMAIL` about problems that need a person, holding back repeats of a key for 15 minutes in memory; it does nothing when the setting is empty. Pass `background_tasks` only on a successful response, since background tasks don't run after an error. Today it covers oversold and deleted products in `fulfill_checkout()`, failed webhooks (which then return 500 so Stripe retries), Stripe errors in checkout and refunds, and unhandled exceptions (the `report_server_errors` middleware in `app/main.py`, keyed per route). Email failures are only logged. `python -m app.alerts` sends a test alert.
- **Rate limits:** `app/rate_limit.py` counts requests per client IP in memory over a one-minute window. Add `dependencies=[rate_limit("auth")]` (or `"lookup"`, `"checkout"`) to a route; each group has one allowance per client, set by `<GROUP>_RATE_LIMIT_PER_MINUTE` (0 turns it off) and read on every request. Over the limit is a 429 with a `detail` and `Retry-After`.
- **Password reset:** `POST /auth/forgot-password` gives the same answer for unknown emails and sends at most one link per user per minute. The `PasswordResetToken` table stores only the SHA-256 of the emailed token. `POST /auth/reset-password` uses a link once, cancels the user's other links and ends the user's sessions (`revoke_sessions`).
- **Products:** each product is a single item with one size, one color and one stock count (no variants). The storefront lists `GET /products/active`, which leaves out inactive and sold-out (`stock_quantity` 0) products, so restocking brings an item back on its own. `GET /products/{id}` still returns them for carts, and the full `GET /products/` list is admin-only. Size and color are free text, trimmed by `clean_label()` (blank becomes `null`, 50 characters at most). The admin form suggests presets from `frontend/src/utils/productOptions.ts`, which also sets the size filter's order. On update, a field sent blank clears it and a field left out is kept, which `sent_form_fields()` tells apart because FastAPI reads a blank form field as missing.
- **Cart:** the server cart (`/cart`, login only) belongs to accounts; guests keep theirs in the browser. Adding a product already in the cart raises that row's quantity rather than adding a row. Quantities are 1 to `MAX_CART_QUANTITY` (`app/schemas/cart_item.py`) and can't be raised above stock; lowering is always allowed, since stock can fall below what's in a cart. The cart page flags sold-out, inactive and over-stock lines and holds Checkout until they're fixed. `POST /cart/merge` adds a guest's browser cart after login, capping at stock and the maximum and skipping inactive or missing products.
- **Uploads:** product images go through `save_uploads()` in `app/routes/product.py`. It checks every file (image extensions only, 5 MB each) before writing any, saves under random names in the module-level `UPLOAD_DIR` (from `upload_dir()` in `app/settings.py`), and returns absolute URLs built from `PUBLIC_API_URL` (falling back to the request's base URL). The product create/update routes are plain `def` so this I/O runs in FastAPI's threadpool.

## Frontend architecture

- `frontend/src/api/axiosClient.ts` calls `VITE_API_URL` (locally `http://127.0.0.1:8000/api`) with `withCredentials` (cookie auth). That is a different site from `localhost:5173`, which is why the cookie defaults to `SameSite=None`.
- API helpers live in `frontend/src/api/*`. Use `apiErrorMessage()` from `api/errors.ts` to show FastAPI `detail` errors (including the first 422 validation message).
- App-wide state (auth, cart, categories) is in `frontend/src/context/`. Each provider (`AuthContext.tsx`, `CartContext.tsx`, `CategoriesContext.tsx`) exports only its component, as React Fast Refresh needs; pages use the hooks `useAuth`, `useCart` and `useCategories` from `useAuth.ts`, `useCart.ts` and `useCategories.ts`, and the guest cart's storage and cart helpers (`MAX_CART_QUANTITY`, `cartErrorMessage`, `removePurchasedFromGuestCart`) are in `guestCart.ts`. Forms that start from a record (the admin edit modals, the address picker) mount fresh with a `key` and take their initial values from props, rather than copying props into state in an effect. The cart (`useCart`) is the one cart API for pages: it uses the server cart when logged in and localStorage (`guest_cart`) for guests, merges the guest cart through `/cart/merge` on login, and `reload()` re-runs its loader (cancelling any load in flight).
- Routes and the public-only/protected/admin guards are in `frontend/src/router/AppRouter.tsx`. Shopping is open to everyone: products, cart, checkout, `/order-success` and `/track` (lookup form) and `/track/:order_number` (token link). `/account` and `/orders` need a login, and `ProtectedRoute` passes `state.from` so login (and register, which forwards the state to login) returns there. `components/orders/OrderView.tsx` renders one order for both the account order page and the tracking page.
- Store identity (name, wordmark, support email, business details, return window, optional policy URLs, and the home page's headline, hero and banner images and events link) comes from `frontend/src/config/store.ts`, which reads `VITE_*` variables. A store's own photos go in `frontend/public/custom/` (gitignored except its README) and are referenced as `/custom/<file>`; the repo ships only `assets/default-hero.jpg` (credited in `assets/CREDITS.md`), so don't commit a particular store's photos or copy. `vite.config.ts` fills in a default store name so `index.html`'s `%VITE_STORE_NAME%` title always resolves. The policy and contact pages are in `pages/legal/`, and `components/Footer.tsx` links to them (or to the owner's own policy URLs) on every page except admin.
- Styling is Tailwind 4, with MUI in the admin pages. Tailwind runs as a Vite plugin (`@tailwindcss/vite` in `vite.config.ts`) and is configured in CSS: `src/index.css` has no `tailwind.config.js` behind it. It pins the gray, red, green and blue families to their Tailwind 3 values in `@theme`, and keeps three Tailwind 3 defaults in `@layer base`: gray borders for bare `border`, the pointer cursor on buttons, and white form fields. Use Tailwind 4 class names (`shadow-xs`, `rounded-sm`, `outline-hidden`); any spacing number now works (`w-70` is 17.5rem), so check a class actually applies the size you meant.

## Tests

- **Setup:** `tests/conftest.py` sets every environment variable before importing `app`. Each test gets a fresh in-memory SQLite database with foreign keys enforced (to behave like MySQL), wired in by overriding `get_session`. `TestClient` is not used as a context manager, so the startup checks don't run.
- **Fixtures:**
  - Factories: `make_user`, `make_category`, `make_product`, `make_address`, `add_to_cart` and `make_order` (`make_order(None)` makes a guest order with an email and address copies but no saved addresses; every order gets an `access_token`).
  - Clients: `user_client` and `admin_client` share a single `client`. For tests with several users, use `client` with `auth_headers(user)`. The auth cookie is `Secure` and the test client talks plain http, so it never sends back a cookie a response set; authenticate with a token instead (`create_user_token(user)` or the login response's `access_token`).
  - `upload_dir` redirects uploads to a temp folder.
- **Rate limits and alerts:** the autouse `fresh_rate_limits` and `fresh_alerts` fixtures clear the counts and the held-back alerts around every test. Alerts are off unless a test sets `ALERT_EMAIL`; they arrive in `sent_emails` like other email. Log lines are checked with `caplog`. Tests of a limit set it low with `monkeypatch.setenv("AUTH_RATE_LIMIT_PER_MINUTE", "3")`.
- **Email:** the autouse `sent_emails` fixture replaces `app.mail.deliver` and returns the list of `EmailMessage`s the app sent.
- **Stripe:** Stripe is never called. The autouse `stripe_customers` fixture in `tests/conftest.py` fakes `stripe.Customer.create/modify` and records the calls. Tests build objects with `stripe.<Type>.construct_from(...)` and monkeypatch `stripe.checkout.Session.create/retrieve`, `stripe.Webhook.construct_event` and `stripe.PaymentIntent.retrieve` (see `tests/api/test_payments_api.py`, whose `guest_checkout_session()` builds a paid guest session).
- **Layout:** tests are split into `tests/unit/`, `tests/api/` and top-level files (app wiring, migrations). The test folders have no `__init__.py`, so test file names must be unique across folders. Import shared constants with `from conftest import TEST_PASSWORD`.
- **Warnings:** `pytest.ini` hides only the deprecations the app is known to use (`datetime.utcnow()`, `on_event`, class-based Pydantic `Config`); any other warning shows in the test summary.
- **Expiry gotcha:** after a request changes data, call `session.expire_all()` before reading it back through the test `session`. Keep ids in local variables, because expired ORM objects can't be read once their row is gone.
